# معیارهای پذیرش امنیت، محرمانگی و انتشار وکیل‌یار
نسخه سند: 0.1.0
وضعیت: پیش‌نویس مستندات؛ پیاده‌سازی و تأیید حقوقی نشده است

## 1. دامنه و اصل بنیادین
وکیل‌یار برای راهنمایی اولیه حقوقی و مدیریت ارتباط با وکیل طراحی می‌شود. پاسخ سامانه جایگزین بررسی پرونده توسط وکیل دارای صلاحیت نیست. این سند معیارهای آزمون را تعریف می‌کند و به‌معنی موفقیت آزمون‌ها یا آمادگی انتشار نیست.

## 2. جداسازی هویت و نقش‌ها
- کاربر عمومی، وکیل، مدیر و سامانه باید نقش‌های مستقل و حداقل دسترسی لازم داشته باشند.
- نشست کاربر عمومی نباید به پنل وکیل یا مدیر دسترسی پیدا کند.
- احراز هویت و مجوز دسترسی باید در سمت سرور کنترل شود.
- پیوند دادن شناسه ناشناس قبلی به حساب ثبت‌نام‌شده فقط با اثبات مالکیت نشست و آزمون حفظ تاریخچه/اعتبار انجام شود.
- تغییر نقش، غیرفعال‌سازی حساب و خروج باید نشست‌های مربوط را بی‌اعتبار کند.

## 3. محرمانگی پرونده و داده
- پرسش و پاسخ خصوصی موکل نباید وارد دانش عمومی یا نمایه عمومی شود.
- پنل وکیل فقط فیلدهای ضروری پرونده را دریافت کند؛ شناسه‌ها و داده‌های غیرضروری حذف شوند.
- متن کامل پرونده در گزارش خطا، لاگ، ابزار تحلیل یا اعلان عمومی ثبت نشود.
- دسترسی مدیر و پشتیبانی به محتوای پرونده باید محدود، دارای دلیل، زمان‌دار و قابل حسابرسی باشد.
- داده‌های حقوقی باید از داده‌های آموزشی و محتوای عمومی جدا نگهداری شوند.
- سیاست نگهداری، حذف، خروجی‌گیری و پاسخ به رخداد افشای اطلاعات باید پیش از عرضه عمومی اعلام شود.

## 4. صحت حقوقی پاسخ‌ها
- پاسخ باید حوزه قضایی و تاریخ/نسخه منبع قانونی را مشخص کند.
- استناد قانونی باید به ماده مرتبط و متن قابل بررسی متصل باشد؛ شماره ماده یا رأی نباید حدس زده شود.
- اگر منبع معتبر یا اطلاعات کافی وجود ندارد، سامانه باید عدم قطعیت را روشن بیان کند و سؤال تکمیلی بپرسد.
- موضوعات حساس یا نیازمند بررسی اسناد باید به مشاوره وکیل ارجاع شوند.
- بسته‌های منبع محدود، مانند گزیده مواد اجاره، پایگاه جامع قوانین محسوب نمی‌شوند.
- تغییر قانون، اصلاحیه و رویه قضایی باید با فرایند بازبینی منبع به‌روزرسانی شود.

## 5. حساب کاربری و ارتباط ایمیلی
- گذرواژه‌ها فقط به‌صورت هش امن و مقاوم ذخیره شوند؛ هرگز از طریق ایمیل ارسال نشوند.
- توکن تأیید ایمیل یک‌بارمصرف، زمان‌دار و در پایگاه داده به‌صورت هش نگهداری شود.
- محدودیت تلاش ورود، ارسال مجدد ایمیل و نرخ درخواست‌ها باید آزمون شود.
- تغییر ایمیل باید نیازمند تأیید مالکیت نشانی جدید باشد.
- کلیدهای سرویس ایمیل و اتصال‌ها فقط در متغیرهای محیطی امن نگهداری شوند.

## 6. مسیریابی API و محدودیت استقرار
- هر مسیر عمومی باید در فهرست مجاز مسیریاب ثبت شود.
- مسیر ناشناخته، مبهم یا دارای route selector نامعتبر باید 404 یا خطای کنترل‌شده بدهد.
- بدنه، هدر، کوکی و پارامترهای درخواست باید بدون نشت بین مسیرها حفظ شوند.
- تعداد توابع استقرار باید با محدودیت پلن انتخاب‌شده سازگار باشد.
- آزمون‌های رگرسیون باید همه مسیرهای موجود را پوشش دهند.

## 7. سهمیه و ذخیره‌سازی
- سهمیه مصرف باید اتمیک باشد تا درخواست‌های هم‌زمان باعث مصرف یا اعتبار منفی نشوند.
- خطای اتصال Redis/Valkey نباید میزبان، رمز، URI یا پیام خام سرویس را افشا کند.
- انتخاب Valkey برای Preview نباید مسیر ذخیره‌سازی Production را تغییر دهد.
- Production باید به‌صورت مستقل از متغیرهای Preview پیکربندی شود.
- خطای سرویس ذخیره‌سازی باید پیام امن و قابل اقدام ارائه کند و باعث دور زدن سهمیه نشود.

## 8. ماتریس آزمون پذیرش
| حوزه | آزمون | معیار قبولی | مدرک |
|---|---|---|---|
| نقش‌ها | ورود کاربر و وکیل | دسترسی متقاطع رد شود | نتایج API و نشست |
| نشست | خروج و انقضا | توکن قبلی بی‌اعتبار شود | آزمون رگرسیون |
| ثبت‌نام | تأیید ایمیل | توکن یک‌بارمصرف و زمان‌دار باشد | گزارش آزمون |
| تاریخچه | تبدیل شناسه ناشناس | تاریخچه و اعتبار فقط برای مالک منتقل شود | آزمون دو حساب |
| محرمانگی | پاسخ API پنل وکیل | فقط فیلدهای ضروری بازگردد | نمونه پاسخ پالایش‌شده |
| لاگ | خطای اتصال/پرونده | هیچ داده حساس یا راز ثبت نشود | بررسی لاگ ساختگی |
| حقوقی | سؤال با استناد مشخص | ماده و منبع قابل تطبیق باشد | پرونده آزمون حقوقی |
| حقوقی | منبع ناکافی | عدم قطعیت و ارجاع مناسب | خروجی آزمون |
| مسیریاب | همه مسیرها | مسیرهای ثبت‌شده کار کنند | تست registry و dispatch |
| مسیریاب | مسیر ناشناخته | پاسخ کنترل‌شده 404 | تست منفی |
| سهمیه | درخواست هم‌زمان | رزرو/آزادسازی اتمیک | تست concurrency |
| Valkey | خطاهای TLS/auth/refused | فقط کد تشخیصی مجاز نمایش داده شود | تست واحد |
| جداسازی محیط | Preview در برابر Production | تغییر Preview روی Production اثر نگذارد | تنظیمات و تست محیط |
| بازیابی | نسخه پشتیبان | بازیابی واقعی و قابل تطبیق باشد | گزارش بازیابی |

## 9. دروازه‌های پیش از انتشار
- CI کامل روی آخرین commit شاخه نهایی سبز باشد.
- تمام PRهای زنجیره‌ای با ترتیب پایه/شاخه صحیح بازبینی شوند.
- Preview قابل دسترس و آزمون دستی کاربر عمومی و وکیل انجام شود.
- آزمون امنیتی جداسازی نقش‌ها، محرمانگی، لاگ و نرخ درخواست اجرا شود.
- منبع حقوقی نمونه‌ها با منبع رسمی جاری و بازبینی وکیل تطبیق داده شود.
- اتصال ایمیل و پایگاه داده در محیط Preview با داده آزمایشی تأیید شود.
- تفاوت Preview و Production، سهمیه، پشتیبان و روش بازگشت مستند شود.
- هیچ داده واقعی موکل در آزمون اولیه استفاده نشود.

## 10. ممنوعیت‌های ایمنی
- هیچ راز، گذرواژه، توکن، نشانی اتصال یا متن خصوصی پرونده در Git یا گزارش عمومی ثبت نشود.
- تغییر Production، ادغام PR، تغییر متغیر محیطی، خرید پلن، مهاجرت داده یا انتشار بدون مجوز صریح انجام نشود.
- سبز بودن CI یا READY بودن Deployment به‌تنهایی اثبات‌کننده صحت حقوقی یا آمادگی انتشار نیست.

## 11. گزارش وضعیت
هر آزمون باید با تاریخ، commit، نتیجه، شواهد و خطا ثبت شود. در نبود مدرک عبارت «در این نوبت قابل راستی‌آزمایی نبود» استفاده شود. وضعیت‌های مجاز: طراحی‌شده، در حال اجرا، اجراشده اما آزمایش‌نشده، آزمایش‌شده و موفق، آزمایش‌شده و ناموفق، متوقف/فاز صفر.
